## 二、模型与口径

- 配置模型 `deepseek-chat`，实际返回 `deepseek-flash`；temperature 0；30 题**全部返回 JSON**，0 次格式失败。
- **每题只跑一次**；首版计划编译失败时按产品行为给一次编译修复（与 2026-10-17 的 12 道评测同一口径），不重跑、不取最好。
- 走 `buildPolicyText` + `compilePlan` + 同一套救援链；**没有**协调器的原生工具循环、`scene.inspect` 与 UI 确认。读数更接近“模型能否给出可编译、可核验的计划”。
- 总耗时 **76.0 s**（30 题串行）。

## 五、硬失败 5 道

- **`joint-06`**：计划里的后两笔引用了 `solid-1:e0`，编译期报 `host_not_found`。这是动作契约/宿主引用错误，不是几何能力不足。
- **`joint-11`**：多面体 `ABCDEF` 的两只面环自交，`degenerate_polyhedron` 拒收。
- **`joint-13`**：三棱柱 + 四棱锥组合体的一个面环不共面，偏差 1.73（√3），拒收。
- **`joint-14`**：模型给出的“鳖臑”坐标不满足 `AC⊥CB`（残差 0.6）与 `AN⊥PC`（残差 0.73），几何核验拦下。
- **`joint-17`**：渐近线等边三角形条件实测 0.65634（题设要求 0），坐标不满足。

## 六、未全过的主要归因

1. **解析器缺口（出现最多）**：8 次报“这条曲线方程没有被归入本仓支持的三类标准圆锥曲线”，集中在 `椭圆C：…`、`圆M：…`、`y=x²/4` 这类写法。对应 `joint-18/20/24/26/27/28/30`（以及 `joint-17` 的第二条核验）。这些题大多已经把曲线画出来了，卡在“认不出方程”。
2. **条件被切碎**：`joint-04` 的 `∥FE`、`joint-05` 的 `=AA₁`、`joint-15` 的 `y=m`、`joint-21` 的直线条件、`joint-29` 的交点条件，都是原文被切成不完整片段后失去判据。
3. **点名映射缺失**：`joint-02`、`joint-13` 这类“两只闭合多面体”没有可靠的顶点名映射，核验器只能说“未核验”。
4. **真正的坐标错误**：`joint-14`、`joint-17`；这类是模型该自己算对的，不能算解析器的账。

## 七、与 2026-10-17 的 12 道怎么比

两者**不是同一题集**，不能直接比较：

- 12 道是 HighMATH 的公开子集，且经过多轮救援/解析修补；最好读数 11/12 可画、8/12 全过。
- 本次是**没调过的联考新卷**：25/30 可画，但题设全过只有 2/30（实质 1/30）。
- 更值得注意的迁移信号：生成不是主要瓶颈（83%），瓶颈已经转到“**把题面条件点亮成核验**”——解析器识别与点名映射。`joint-24` 只落了 1 个椭圆图元、`joint-27` 落了 8 个图元，图都在，读数却停在“未核验”。

## 八、边界

- **单次、单模型**（flash）、单次修复；没有跑 v4-pro，也没有多次平均。
- 这是批量 harness 的读数，不是完整 App 的协调器原生工具循环与 UI 确认；真实 App 可能不同（通常更慢，但能看到草稿/确认/撤销）。
- **「无核验项」不等于画对**，只表示这一题没有解析出可核对义务。
- 题面只保留图形描述部分，原题中纯求解的第（2）/（3）问可能被省略；这不影响“图形是否按条件画出”，但会影响与整题得分的比较。
- 没有人工目视验收，也没有把图渲染成截图逐个检查。

## 十、后续建议（2026-10-20 更新：第 1 条已部分实施）

- ~~先修解析器的"命名圆锥曲线"识别~~ **已实施一半（2026-10-20，随 v4.0 之后的维护批次）**：
  - **标签冒号**（`椭圆C：…`、`抛物线C：…`、`双曲线C：…`）**已能读**。根因是 `parseDiagramObligations` 里那条"后缀守卫"（本意是别把 `∠ABC=60°` 的后缀当成 `BC=60`）把**标签冒号**也一起挡了；现在只给椭圆 / 双曲线 / 抛物线六条读取器开了一个窄开关 `allowAfterLabelColon`，比例写法 `AE:AD=2:5` 仍被原守卫挡住（有反向用例钉着）。覆盖 `joint-24`、`joint-26`。
  - **函数式抛物线** `y=x²/4` / `y=2x²` / `x=y²/4` **已能读**（`y=x²/4` ⇔ `x²=4y` ⇒ `p=2`）；**被平移过的** `y=x²/4 + 1` / `− 1` 明确不认（顶点不在原点，焦点准线都变了）。覆盖 `joint-28`。
  - **圆的一般方程**（`圆M：x²+y²−4x+2y−4=0`）**已能读并核验**（2026-10-20 续）：`x²+y²+Dx+Ey+F=0` ⇒ 圆心 `(−D/2, −E/2)`、半径 `√((D²+E²)/4 − F)`；右端写成 `=4` 也收。判据**圆心与半径各自比**（只比半径的话，位置挪了三格的圆会被判通过）。覆盖 `joint-27` 的方程写法。
  - **仍未做**：`椭圆C：x²/a²…` 与 `x²=2py` 这类**符号系数**（没有数值，正确做法就是继续落未核验，不许猜成 1）；`joint-30` 的"双曲线过两点"是**条件类型**缺口，不是方程写法。
  - **本批没有重跑真实 provider 的 30 题**：这些收益是"方程终于被认出来、图元不再停在未核验"，**不是**"这几道题已经全过"。
- ~~再补"闭合多面体顶点名映射"，让 `joint-02`/`joint-13` 这类多体组合能核验~~ **已实施（2026-10-20）**：多只闭合多面体现在按**执行顺序**与各自物化出来的新多面体配对 —— 配的是**计划动作**与**它自己的图元**（点名仍然只从动作的 `vertexNames` 来，**不是**按题面顺序猜坐标）；数量对不上、或两只用了同一个点名，仍然拒绝并说清是哪一种。覆盖 `joint-02` 的"两只闭合多面体"。`joint-13` 还有**面环不共面**那一半（内核侧），本批没动。
- 生成侧优先修 `host_not_found`（`joint-06`）与组合体面环（`joint-11`/`joint-13`），它们直接导致 0 图元。**两者都已补上修复提示（2026-10-20）**：`host_not_found` 说清"别名必须是前面某一笔真的给出的名字，别自己拼 `solid-1:e0`"；**面环**那两支按几何诊断分流 —— `is not coplanar` ⇒ 说清"每一圈必须共面、组合体不要把两只立体的点混进同一圈、平面片用 `solid.create_face`"；`self-intersects` ⇒ 说清"这是**顺序**问题，沿边界顺序绕一圈，别靠挪坐标解开"。**内核没有改**：这两种输入仍然被拒（拒得对），变的只是模型下一轮拿到的**改法**。`joint-13` 里"面环不共面"是模型给的坐标本身不成立，不能靠系统重排掩盖。
- 若要判断"真实 App 的效果"，应另跑一次完整协调器/UI 路径，不要拿本文的批量 harness 数字代替。
