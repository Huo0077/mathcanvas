# 欠定图形的见证生成与关系核验 设计

**日期：** 2026-10-03 ｜ **状态：** **已按本设计实现（7 个 Task 全部完成），在分支 `feat/underdetermined-witness-relations` 上——尚未合并进 `main`、未打包、未发布**（实施计划 [`../plans/2026-10-03-underdetermined-witness-relations-implementation-plan.md`](../plans/2026-10-03-underdetermined-witness-relations-implementation-plan.md)；当次读数：全库单测 281 文件 / 3250 通过 + 1 todo / 0 失败，两个包 typecheck exit 0）｜ **来源：** 用户现场报障——「在四棱锥 P-ABCD 中，PA ⊥ 平面 ABCD，BC ∥ AD，AB ⊥ AD」这类**只有关系、没有数值**的描述画不出来

## 1. 用户工作与验收

用户在 Agent 工作区里贴一句**只有关系、没有数字**的题面（例如「在四棱锥 P-ABCD 中，PA ⊥ 平面 ABCD，BC ∥ AD，AB ⊥ AD，画出这个四棱锥」），得到一只**满足全部所述关系**的四棱锥，而**不是**「请补充数值」的反问。

同时用户能看见系统替他定了什么：哪些数是系统选的、每条关系是否真的成立，并且**可以改**。

**验收判据（都可复核，且不靠"看起来对"）：**

1. **形状与标注保留**：顶点名 P / A / B / C / D 与题面一致（P 是锥顶、ABCD 是底面）。
2. **每条所述关系逐条成立**：用内核已有的 `constraints3d.ts` / `geometry3d.ts` 判据算残差，**每一条都在容差内**。
3. **关系核验是执行前的判据，不是事后注释**：核验失败的候选**不进入草稿**。
4. **透明**：每条被系统定下来的数值都产出 `StructuredAssumption`（`kind: "witness"` 或 `"inferred"`），且 `overridable: true`。
5. **可改**：用户在属性栏改这些数值后，文档随之更新（沿用既有的属性栏编辑与一步撤销路径）。
6. **不静默**：没有任何一条系统选择的值是"用户看不到"的。
7. **重试后仍不成立时如实报错**，不产出一张部分满足关系的图。

## 2. 决定记录（2026-10-03，用户逐项确认）

| # | 问题 | 用户决定 |
| --- | --- | --- |
| 1 | 系统自动补的数值，用户要知道是系统选的、并且能改吗 | **明确告知 + 可改**：沿用既有 `assumptions` 通道，不新造静默路径 |
| 2 | 这套数值怎么来 | **模型生成候选解 + 系统逐条校验**（不是系统硬编码默认构造，也不是只保留符号参数） |
| 3 | 模型凑不出满足全部关系的坐标时 | **自动重试一次，再不行就问用户**（不画尽力而为的残图） |
| 4 | 第一批支持哪些关系 | 内核已能判定的那几类（⊥ / ∥ / 共面 / 点在面上）**再加上**长度相等、比例、中点等**度量关系** |
| 5 | 「题目给了哪些关系」由谁列出 | **模型在计划里声明 + 系统用原话关键词做覆盖度校对**（漏声明即报错） |
| 6 | 方案与落地顺序 | **方案一**（关系声明表 + 见证残差核验），**先立体、后平面** |
| 7 | 关系挂在什么对象上 | 第一批只支持**顶点**，以及由顶点导出的方向（线 = 两点之差，平面 = 三点的法向）——覆盖报障那类题面，且不需要新的目标解析 |

**决定 2 的已知代价（如实记）：** 模型可能反复算错，浪费 token 与轮次；换来的是普适性（任何形状、任何关系组合）与**不把几何判据搬进系统**（内核只判定"算得对不对"，不替模型猜坐标）。

**决定 4 的已知代价（如实记）：** 度量关系（比例、中点、等长）内核**没有现成残差**，需要按既有原料组装，并自证容差口径与内核同源（见 §5.3）。

## 3. 现状审计（都是实读，带 `文件:行`）

**这不是一个新子系统。** 仓库里已经有一套欠定特值机制，规格 §6.3 已经把优先级写好了：

- `packages/agent-core/src/underdetermined.ts:1-30` 的文件头就是那段规格原文：**「欠定选择优先级：满足显式约束、保持非退化、避免特殊对称、使用小整数、最小化复杂度。若问题要求"任意""恒定""定值"，必须保留符号参数，不能特值化成单点。」**
- 同文件 `:207` 的 `selectWitness(request)` 已经实现了这条顺序：`:210` 先判符号（`isInvariantRequest`），`:216` 再用显式约束，`:236` 才轮到候选挑选。
- **契约里已经有这一档**：`packages/agent-core/src/contracts.ts:267` 的 `StructuredAssumption.kind` 已经是 `"safe_default" | "inferred" | "witness" | "symbolic"`；`:271` 有 `overridable`。
- 已有的见证族只有四种：`underdetermined.ts:32` 的 `WitnessKind = "triangle" | "slope" | "prism" | "moving_point"`。
- 验证函数是**导出**的：`validateTriangleWitness`（`:124`）、`validatePrismWitness`（`:133`）。**这一点很重要**——说明"接受外部给的候选、用内核判据筛"本来就是这套机制的设计形状，本次只是把候选来源从常量表（`witnessTriangleCandidates()`，`:166`）扩到模型给的候选。

**真正缺的两件事：**

1. **没有多面体族**。不规则立体在动作层的唯一入口是 `solid.create_polyhedron`（`actionRegistry.ts:447-452`，`vertices` / `faces` **必填、零默认**），而 `WitnessKind` 里没有它——于是"四棱锥 P-ABCD + 关系"这条路**根本没有出口**。
2. **关系核验不存在**。优先级第一条「满足显式约束」目前**只被用来检查退化**：
   - `validateTriangleWitness` :124-130 —— 只问内核"这个三角形退化不退化"；
   - `validatePrismWitness` :133-136 —— 只问 `validatePrismInput` 共面 / 自交 / 零体积。
   - **没有任何地方验证"PA ⊥ 平面 ABCD"这类题目显式给出的关系。**
   - 内核**已经有**这类残差：`geometry-kernel/src/constraints3d.ts:122-131`（`coplanar` / `parallel` / `perpendicular`），原料齐备（`geometry3d.ts:12-44` 的 `addVector3` / `subtractVector3` / `scaleVector3` / `dotVector3` / `crossVector3` / `lengthVector3` / `normalizeVector3`）。

**提示词这一侧是实际卡住用户的直接原因**（两条规则直接冲突）：

- `apps/web/src/agent/systemPrompt.ts:97`：「澄清（信息不足时用它，**不要编数值**）」
- `apps/web/src/agent/systemPrompt.ts:260-263`：「## 先做，别反问 …… 只有表里标着「必须问」的字段缺失时才返回 `clarification`」
- `apps/web/src/agent/systemPrompt.ts:192`：「题目要求「任意 / 恒定 / 定值」时：**必须保留符号参数**……不要特值化成一组具体数字」

四棱锥的关系**既不是"表里有默认值的字段"**（`actionRegistry.ts:356-358` 的 `size` 默认只覆盖 `cube` / `pyramid` 模板，`solid.create_polyhedron` 一条默认都没有），**也不在"必须问"的字段表里**（`:403-404` 只有球的 `center` / `radius`，`:434` 只有正 N 棱锥的 `sides`）。于是模型在这两条规则之间没有正确出口。

**本地确定性规划器不在这条路上**：`apps/web/src/agent/localPlanner.ts:306-340` 是"没有接入模型服务时"的过渡件，只认几条固定指令。本设计**不动它**（它认不出时就该老实问，见该文件 `:303` 的纪律）。

## 4. 方案取舍

**采用方案一**：计划信封新增一张**关系声明表**，模型为它给出坐标见证；系统在**执行前**用内核残差逐条核验「声明的每条关系真的成立」，并把这条核验接进**既有的一次性修复回路**。

被否掉的方案：

- **方案二（只做关键词覆盖度，不做残差核验）** —— 验证退化成"模型说自己验过了"，内核已经写好的残差判据**一条都用不上**。用户要的是"自动补值"，而**补错的值比不补更危险**，所以判据必须由内核给。**否。**
- **方案三（把关系建成文档里的真约束，画布按关系解坐标）** —— 教学价值最高（拖动时关系不失效、真正实现"任意"），但那是一个**新的求解子系统**，会牵动文档格式、`.mgeo` 往返与画布重建，工作量与风险高一个量级。**本批不做**，记为后续方向。

## 5. 设计

### 5.1 关系模型（本次唯一的新接口）

计划信封（`contracts.ts:228-231` 的 `PlanEnvelope`）新增**可选**字段 `relations`，与既有的 `assumptions?` 并列、同样可选，**不改三个分支的形状**。

每条关系是一个简单形状：

```
{ kind: "perpendicular" | "parallel" | "coplanar" | "pointOn"
      | "equalLength" | "ratio" | "midpoint",
  targets: RelationTarget[],
  value?: number }
```

**`RelationTarget` 只复用既有引用形式**：`{ scope: "draft", alias }` 加上在顶点数组里的下标（例如 `{ alias: "pyramid", vertex: "P" }`）。系统只做**名字 → 坐标**的映射，**不解析表达式、不引入几何类型系统**。

- 理由：判据因此是**精确**的（验的是模型自己写下来的表，不是系统去猜自然语言），残差可以逐条报给用户；代价是带自由参数的表达式关系不在第一批。
- `faces` / 线 / 平面这类目标：第一批只支持**顶点**与**由顶点导出的方向**（线 = 两点之差，平面 = 三点的法向），这覆盖了用户报障那类题面，且不需要新的目标解析。

**一条待实施期核实的开放项（如实记）：** 需要确认计划信封的解析层（`outputParser.ts` / schema 校验）对**新增可选字段**是"容忍"还是"白名单之外一律拒"——提示词里写着"多一个字段都会被拒绝"（`systemPrompt.ts:204`），而信封上已有的 `assumptions?` 说明可选字段是能加的。实施第一步就是把这条核实清楚，并**在测试里钉住**（`relations` 缺省时行为与今天**逐字相同**）。

### 5.2 覆盖度校对（决定 5）

系统从**用户原话**（不是模型的转述）里抠关系关键词，要求 `relations` 表**逐条回应**：

- 关键词表与提示词**共用同一份常量**（沿用 `underdetermined.ts:84` 把关键词写成唯一来源的既有做法，避免两份判据分叉）。
- 第一批关键词：`垂直` / `⊥` / `平行` / `∥` / `共面` / `相等` / `中点` / `比例` / `:`（比例另加数字形状判断）。
- **原话出现某关键词而 `relations` 表里没有对应 `kind` 的条目 → 报覆盖度错**，路径指到 `envelope.relations`，走修复回路。
- 覆盖度**只查"有没有回应"**，不试图从自然语言里抠出"是哪四个点"——那是模型声明表的职责。这条边界必须写进提示词，否则模型会以为系统也在解析。

### 5.3 残差核验（决定 2、4）

**核验对象**：这次计划**将要产出**的坐标（在草稿物化之前，由 `solid.create_polyhedron` 的 `vertices` / 其它动作的 `inputs` 直接读出）。

**逐条判据**（全部复用内核，不新写几何）：

| 关系 | 判据来源 |
| --- | --- |
| `perpendicular` / `parallel` | `geometry-kernel/src/constraints3d.ts:122-131` 的同源残差（叉积 / 点积，按尺度归一） |
| `coplanar` | `constraints3d.ts:101` 的 `coplanarResidual` |
| `pointOn` | 面内 / 线上判据（由 `coplanarResidual` 与点到线距离组装） |
| `equalLength` / `ratio` | 由 `subtractVector3` + `lengthVector3`（`geometry3d.ts:16, 32`）组装 |
| `midpoint` | 由 `addVector3` + `scaleVector3`（`geometry3d.ts:12, 20`）组装 |

**容差必须与内核同源、只有一处**：仓库已经有一条纪律——「判据来自内核，不是这里自己发明」（`underdetermined.ts:22-29`）。所以**不新写第二套容差**，复用内核既有的按点集尺度缩放策略（`constraints3d.ts` 与 `hosts3.ts:132` 已经这么做），并在测试里钉住"同一组坐标在核验层与内核层得到同一个判定"。

**核验产出的假设文案**（决定 1，给用户看的人话，示例）：

```
- 题目没有给定 AB 的长度，取 AB = 2。
- 题目只说了 BC ∥ AD，取 BC = 3（与 AD 不等，避免把一般情形做成平行四边形）。
- 以上均为系统选取的示例值，可在属性栏直接修改。
```

**「避免特殊对称」这条优先级同样适用**（`underdetermined.ts:143-163` 已经把它写成通用原则）：生成的值**不该**让图形意外退化成更特殊的形状（例如把只是"平行"的 BC 取成恰好与 AD 等长，就把一般梯形做成了平行四边形，会掩盖一般性结论）。这条要作为**候选筛选的一条**实现，而不是只写在注释里。

### 5.4 多面体见证族（补齐缺口的第 1 件事）

- `WitnessKind`（`underdetermined.ts:32`）新增 `"polyhedron"`，`WitnessValue` / `WitnessConstraints` 同步新增分支：`{ vertices: Vector3[]; faces: number[][] }`。
- **用词要与既有族一致**，便于识别：模型给出候选 → 系统按 `selectWitness` **既有的候选循环形状**筛选（不满足关系的候选**跳过并记入 `considered`**）。
- `considered`（`underdetermined.ts:79-81` 已有这个字段）正好用来解释"我为什么没选它"——候选被跳过的理由要**逐条可读**。
- **符号优先规则原样不动**：`isInvariantRequest`（`:86-90`）仍排在**关系满足之前**。题面出现「任意 / 恒定 / 定值」时返回符号结果，**根本不进入候选挑选**（`:210-213` 的既有顺序不得改动）。
- **本设计不改既有规则的适用范围**（这条必须显式写下来，否则实施时会误扩权）：`systemPrompt.ts:192` 那条「任意 / 恒定 / 定值 → 保留符号参数」约束的是**题面确实在要求任意 / 恒定 / 定值**的情形（例如"求证 θ 任意时…恒为…"），那时特值化会**改掉题目的性质**。本设计只在**题面给的是固定图形、只是没给数值**（四棱锥 P-ABCD 那类）时补齐数值。两者的分野**由 `isInvariantRequest` 这一个判据决定**，不新增第二个判据、也不放宽它。

### 5.5 接入点（四层，与现状一一对应）

1. **新模块 `packages/agent-core/src/relations.ts`**：关系表结构、覆盖度校对、逐条残差核验。**这是唯一的判据真源**——`selectWitness` 的候选筛选与 `planCompiler` 的执行前核验都调它，不各写一份。
2. **扩 `underdetermined.ts`**：新增 `polyhedron` 族；候选筛选接入 `relations.ts` 的核验（`validateTriangleWitness` / `validatePrismWitness` 已是导出函数的既有形状，本次沿用）。
3. **扩 `packages/agent-core/src/planCompiler.ts`**：插一层**关系核验**。落点已经查清——`compilePlan`（`:150`）在 `auditPlan`（`:199`）之后已有两条同性质的检查：`validateGeometry`（`:461`，诊断 stage `geometry_validation`）与 `verifyPlan` / `verifyExplicitCubeRequest`（`:516` / `:578`，诊断码 `user_constraint_mismatch`）。关系核验与它们是**同一类东西**，所以走同一个形状：产出 `PlanDiagnostic`（stage `geometry_validation`），并在失败时产出 `RepairRequest`（`allowedChanges` 指到 `envelope.relations` 与相关 `inputs`），由既有的 `describeCompileRepairPrompt`（`:562`）转成人话。
4. **改 `apps/web/src/agent/systemPrompt.ts`**：只改冲突口径（`:97` 与 `:260-263`），把「不要编数值」按新口径改写为**「关系可满足时给见证、不可满足时问用户」**；`:192` 的符号保留规则**一字不动**；并补一条**四棱锥 P-ABCD 正例**（现有正例里没有这类"只有关系没有数"的形状）。
   - 提示词改动必须**同时升 `SYSTEM_PROMPT_VERSION`**（`systemPrompt.ts:27`，`:26` 的注释已经规定"改内容就要改它"）。

## 6. 失败与重试（决定 3）

```
关系核验失败
  → RepairRequest（列失败的关系 + 实测残差 + 只允许改这几处）
  → 模型重试一次（既有的一次性修复回路，不新造回路）
  → 仍不过 → 如实报错 + 回到问用户（clarification）
```

**不静默给残图**：宁可停下来问，也不给一张"看起来像"但不满足题面关系的图——这与「认不出时老实问路，比悄悄改文档好」（`localPlanner.ts:303`、`:324`）是同一条纪律。

## 7. 风险与必须留下的证据

| 风险 | 必须留下的证据 |
| --- | --- |
| **头号风险**：新口径与「任意/恒定/定值必须保留符号参数」冲突 | 一条测试钉住：题面出现「任意」时**绝不特值化**，符号优先**永远排在关系满足之前**（复用 `underdetermined.test.ts` 既有用例形状） |
| 容差出现第二套（核验层与内核层判定不一致） | 测试：同一组坐标在核验层与内核层得到**同一个**判定 |
| 系统"猜"关系而不是只查覆盖度 | 测试：原话有 ⊥ 但表里没声明 → 覆盖度错；表里多声明了原话没有的关系 → **不算错**（模型可以补充题面隐含的关系，但不能漏） |
| 模型声明表算不了的问题被当成系统能力 | 提示词里写清"覆盖度只查有没有回应"，并在测试里钉住系统不做自然语言关系抽取 |
| `relations` 字段的解析容忍性未核实（§5.1 开放项） | 实施第一步的实测 + 测试：`relations` 缺省时行为与今天逐字相同 |

## 8. 明确不做（本批）

- **不做平面几何那一批**（决定 6：先立体、后平面）。但 §5.1 的关系模型与 §5.5 的分层**按平面也能拿来用**的形状设计，第二批只加判据、不改结构。
- **不做带自由参数的表达式关系**（例如"BC = 2t"）。
- **不把关系存进文档**（方案三）。
- **不动本地确定性规划器**（`localPlanner.ts`）。
- **不改「任意 / 恒定 / 定值」的符号保留口径**。
- **不做画布上的"示例值"视觉区分**（用户没选这一档；第 1 问里那一档被明确排除）。
