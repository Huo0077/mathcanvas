## 1. P0/P1/P2：人工自测发现的三个问题（**用户报告，控制器未旁观**）

### P0-A（真 bug）切线题在桌面版失败 —— **报错原文已到手，原先的"数值溢出"猜测被推翻**

- **现象**：7 道自测题里，`画出 f(x)=x³−3x 的图像与它在 x=1 处的切线` 失败，用户描述为"溢出了"。
- **报错原文（2026-10-10 用户从桌面版回传）**：`run_failed` —— **`the plan never matched the schema: invalid_type@envelope.actions[1].inputs.sourceId: expected a string`**。轨迹是：检查环境 ✓ → 读取场景 ✓ → 规划 ✓ → 暂存草稿 **2 action(s)** ✓ → 修复轮（shape 1/1, geometry 1/1）✓ → **失败**。
- **这个原文当场推翻了本计划原先的三条嫌疑**（采样区间过宽 / 取景数值溢出 / 工作区停在 3D）：失败**不在几何或数值层**，而在**计划形状**这一层，而且失败的是 `actions[1]` 的 `inputs.sourceId`（切线的 **源曲线引用**），不是坐标。
- **根因（读代码，已核）**：我们自己的动作表里有**两种**引用写法 —— `dynamic.create_bound_point.host` / `derived.*.solidId` 发布给模型的是**对象** `{scope:"draft",alias:"…"}`（技能自述里还明确这么教），而 `function.create_tangent.sourceId` 是**裸 id 字符串**（`references: [{field:"sourceId", kind:"id"}]`）。模型按前者的样子写了 `{scope:"draft",alias:"f"}` ⇒ 传输层 `boundedString` 判 `invalid_type`，**一次修复轮也没救回来**（错误只说 "expected a string"，没说该写什么）。
- **证据强度**：`e2e/agent-function-tangent.spec.ts` 通过，是因为**夹具**写的是 `sourceId: "draft:f"`（合规写法）——离线夹具替模型写对了，所以这条路径**离线永远照不出来**。
- **修法与判据（下一步动手）**：`kind:"id"` 引用字段**两种写法都收**（草稿作用域对象 ⇒ 摊成 `draft:<alias>`，那是编译器认的唯一别名写法；`scope:"scene"` 照旧拒绝，因为摊平会丢掉跨文档判据），并把**接受的形状**同时写进发布出去的 schema 与拒绝时的报错文本；判据两层 —— 传输层一条（对象写法 ⇒ `sourceId` 解析成 `draft:f`）+ **管线级一条**（`function.create_graph` + 对象写法的切线 ⇒ 真的编出切线，不是"少一条诊断"）。
- **最小复现（不写产品代码的那一步）**：桌面版同一句已由用户跑过并给了原文；浏览器侧按上面那条管线用例复现即可（离线夹具走的是合规写法，所以要**显式喂对象写法**）。

### P1-B 平面 vs 立体：系统不主动区分 —— **已修（2026-10-10），归类为"判据缺失"**

- **归类结论（当场查明，不是推测）**：**判据缺失**。`planWorkspaces` 把 `dynamic.*` 与 `solid.*` / `section.*` 并列算作"要立体几何"，而 `dynamic.create_bound_point` / `bind_curve` / `create_locus` 这一族**自己不要工作区**（由宿主决定，宿主总在同一份计划里由 `planar.*` / `solid.*` 建出）。产品路径上真的会踩：`localPlanner` 的「椭圆 + 切线 + 恒/定值」⇒ `conicInvariantPlan`（椭圆 + 两轴 + 三个动点 + 切线）⇒ 切到**立体几何**；**图照样画得出来**，所以全绿而用户看得见错（原来 `agent-conic-invariant.spec.ts` 里那句"工作区被切到圆锥曲线"只是一句注释）。
- **已落地**：`dynamic.*` 移出判据（中性动作），只有中性动作的计划**不切工作区**；`systemPrompt.ts` 的注释同步更正。
- **判据**：`planWorkspaces(conicInvariantPlan()) === ["conics"]`（单元，拿真夹具）+ `e2e/agent-conic-invariant.spec.ts` 提交后断言 `跳转到平面几何` 的 `aria-pressed=true`。
- **变异**：把 `dynamic.` 加回 ⇒ 两层同时真红（浏览器报 `Expected "true" / Received "false"`），还原复绿。
- **读数**：`typecheck` 0；`lint` 0 error / 13 warning；全库非 Lean **353 文件 / 4118 通过 + 1 todo / 0 失败**；全量 e2e **218 通过 / 0 失败**。

### P2-C（已查实的缺陷）画布顶点标签与核验器 `vertexNames` 可能错位

- **现象**：用户自测"点的名称对不上"。
- **根因（早已查实并记录）**：画布标签由 `templatePointLabel(index)` 按**下标顺序**生成（`apps/web/src/solidTemplates.ts:41`），而核验器按 `vertexNames` 的下标读 ⇒ 题面把顶点写在前面时（`P-ABCD` 这类）**整体错位一格**，"核验通过"可能指另一个顶点。
- **为什么一直没修**：改标签生成顺序会撞 `planCompiler.offPath.golden.test.ts` 的"关旗与 `4707b64` 逐字节相同"契约 —— 那是**已复核的公开契约**，改它必须重新基线并说明理由。
- **裁决（本次直接定，执行时照此办）**：**修**。做法与顺序：
  1. 先写**红**：一条用例，题面 `P-ABCD`（顶点写在前面）+ 一条点名核验 ⇒ 断言"核验里那个顶点 = 画布上那个标签"（今天必红）；
  2. 再改**一处**生成顺序（让标签跟随 `vertexNames` 的下标语义），并**同时**更新 golden 基线（说明"这条字节相同契约因为一个真缺陷被有意更新"）；
  3. 全量 e2e + 定向回归；变异：把顺序改回去 ⇒ 那条红。
- **风险**：golden 基线一动，历史"关旗逐字不变"的证据链要重新落一次；**这是本项目至今最容易被误读成"退步"的一次改动**，所以同步文档时必须逐字写清。
