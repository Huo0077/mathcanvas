## 失败分层及后续优先级

1. **P0 — 修正结构化答案和正文终答一致性**：在交付门禁之前将“无匹配选项 / 需对照原图 / 最终答案不是 A-D”与结构化 `optionId` 的矛盾判为不可交付；不得仅凭隐藏结构字段给未看见的图选项硬记正确。`mm-012`、`text-128` 必须有失败回归。
2. **P0 — 图像证据与重读**：图题 19/30 未交付：11 个有未核对的非外观疑点走等待澄清，1 个由模型主动澄清，6 个因为必需图像证据缺口被拦截，1 个识图结果本身解析失败（`mm-029`）。这不等于只需放宽门禁：需要逐项核查图示标注与数值、可选择区域重读及 OCR 置信，并且所有费用计入共享预算。
3. **P1 — 交付后数学错误**：严格口径的已交付但选错至少 6 道（`mm-033/035/055/059/068`、`text-203`）；另有 `mm-012` 正文不可判与 `text-128` 矛盾。这是实际准确率瓶颈，不能通过路由或格式修复伪装为成功。
4. **P1 — 按入口分轨再验**：完成安全修复后重建并运行小样本针对性真实识图/完整 UI，再上未参与修复的留出卷。继续分列交付、严格选项、结构化选项、一致性、题图证据、推导/图形人工复核；不得从当前开发集承诺“接近 100%”。

## 追加核对：图题相对旧 runtime 轨道的下降归因（2026-11-09）

同一 30 道图题：旧 `core-runtime-with-native-provider` 入口交付 22/30、严格选项正确 15/30；修复后的 `core-service-with-native-provider-auto-vision` 入口交付 11/30、严格正确 5/30。即使题集与保存的模型配置相同，**入口/安全门禁不同、单轮模型输出有波动，不能把差值直接归咎于识图模型**。识图结果可解析比例反而是 28/30 → 29/30，但“可解析”不等于条件正确。

逐题交叉核对旧版原本正确的 15 题：当前 **7 题直接等待用户核对图示、4 题被 `missing_dimension` 拦截、2 题虽交付但选错、2 题仍选对**；另有 3 道旧版未计正确的图题变为正确，净值 15→5。其中 `mm-000` 初始点坐标已在题干明写，但 OCR 仍标为 `condition` 疑点，入口不做跨题干核对便直接转等待；`mm-008` 题干明写容器高 8 cm、水深 6 cm，图形读数列表为空，`requiredImageGaps('volume', audit.facts)` 仅数**图上形式化读数**便报“没有任何可核验的数值尺寸”，这是假阳性拦截；`mm-017` 题干给弧长 8 尺、高 5 尺也被同一逻辑拦下；`mm-009` 图示文字明确“标有尺寸 2、4”，但 `imageDimensionReading` 只认“长/高为数值”及等式而没把这种可追溯描述转成结构化尺寸。`mm-025` 是从给定体积反推半径的题，不能硬要求图上先读到两组独立尺寸。

调用链定位：`apps/web/src/services/problemImageEvidence.ts` 的 `requiredImageGaps` 只接收 `facts`；`eval-results/2026-11-09-refactored-live-20261109-164416/live.eval.mjs` 按 `target` 将该缺口直接传给生产 `startProblemSolve`。`apps/web/src/agent/agentRunner.ts` 对所有未人工标记 reviewed 的非外观疑点直接改走澄清规划器。**更正：**浏览器生产入口 `apps/web/src/components/agent/ProblemImageComposer.tsx` 的 `recognize()` 已调用 `runImageRereadCycle`（上限 2 次），上一句“生产未接线”不成立。**本次评测脚本绕过了这个识图面板**，只调用 `readProblemImages` 并直接把首读的缺口传给服务，既没有区域补读，也没有用户核对；因此这轮 5/30 是“首读直接进服务”轨道的读数，不能据此宣称完整浏览器识图流程同样是 5/30。纯函数对题干已知尺寸的误拦截仍在产品识图面板中，因为它也调用同一 `requiredImageGaps`。应先分“题干数字/图上数字/网格尺寸/符号量/可由其它条件推得”，对具体缺口做受控重读并重新审计，仍不能把无法确认的条件擅自认成正确。

## 图题修复实施记录（尚无重新付费实测）

针对上面的确定性误拦截，现有工作树增加了下列守卫：

- **共享体积缺口判据**现在合并 OCR 题干明确写出的容器高／水深、弧长／高度与可追溯图上数字，但不把选项数值当题设，也不把“网格小格边长为 1”冒充完整实体尺寸；“仅圆柱半径”仍保持缺口。修复 `mm-008`、`mm-017` 类型的误判，并保留 `mm-005` 类型的真正不全。读数只用于“是否还缺输入”而不是数学正确证明。
- **目标题型判定**区分“给定体积求表面积”和“要求体积”。修复 `mm-025` 一类被错误送入体积缺口的情况；题干选择项被切除后才判目标。
- **无定位框的图像补读**：首读未给任何可追溯位置、确实缺少必需图上条件时，在已授权附件内允许一次全图补读；无新增信息立即停止，保留缺口，绝不编造坐标或消除尚无来源的证据。浏览器的 `ProblemImageComposer` 原本已有有界重读，此处补齐“零定位框”的断点，并让题干尺寸判据同时用于首读、重读、最终送题。
- **可见终答/隐藏结构冲突**：结构化选项声称 A/C，正文却写“无匹配选项／需对照选项图／最终答案不是同一字母”时，产品服务端按 `inconsistent_final_option` 拒绝交付；覆盖了上轮 `mm-012`、`text-128` 类型假阳性。

修复仅经过脱网的红→绿回归、生产服务注入回复测试和 Web 图题组件测试；先前同 50 题 **5/30** 仍是修复**之前**“首读直接进服务、不走浏览器面板补读”的真实调用读数。没有再调用用户 API 密钥，不得外推图题已恢复到旧版 15/30。用户若要比较完整浏览器流程，必须固定新版本、操作完整识图面板、给出请求上限并复核人工选择与推导，且按同入口对比。
