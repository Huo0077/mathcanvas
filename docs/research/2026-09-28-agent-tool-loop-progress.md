### Live run against a real provider (2026-09-29)

A real provider became available on the author's machine (DeepSeek, `deepseek-chat`, `tools` capability **verified**), and one conic-section problem was driven through the **project's own planner** — real system prompt, action registry, native tool channel, multi-round loop, reference resolution — with only the injected provider transport swapped for a direct HTTP call:

> 已知椭圆 C 的中心在原点，焦点在 x 轴上，经过点 P(2, 1)，离心率为 √2/2。求椭圆 C 的标准方程。

- The model **derived the answer itself** and put the derivation in `assumptions`: `e=√2/2 ⇒ b²=a²/2`, then `P(2,1) ⇒ a²=6, b²=3`. Independently checked: `x²/6 + y²/3 = 1` is correct.
- It emitted two actions: `planar.create_conic` (`radiusX=√6`, `radiusY=√3`, `axis="x"`, `label="C: x²/6+y²/3=1"`) and `planar.create_point` (`P(2,1)`). Whole run: **2.3 s**, one round.
- Transport log: `POST https://api.deepseek.com/v1/chat/completions  messages=2 tools=5` — **5 tools is exactly the model-facing set** (4 read + `plan.set_plan`), so the native tool channel really does publish tools on a live provider.
- **Two findings, both about this repo rather than the model:**
  1. On the first attempt the fixture passed `tools: []`, and the model's `plan_set_plan` was rejected with `the provider returned a tool call (plan_set_plan) that no tool schema of ours asked for`. The rejection was correct; the fixture was wrong. Taking the tool list from `createToolRegistry().forModelPhase(...)` fixed it — and this is live-provider evidence that the "only tools we published" criterion works.
  2. **`deriveAcceptance` returns `[]` for this problem**, because its shape table has no conic section (it covers cube / tetrahedron / prism / section / point only). So the completion gate stayed inert for this run — a real gap: **conic-curve problems currently get no "did it finish" judgement.**
- Honest limits: the scene was **not** connected (the read tools would have returned an empty stub), so the multi-round observation loop was never exercised by this run; and one problem is not a pass@1 measurement.

- **Phase 6 next step, change surface measured (2026-09-29): persisting `ToolCallTrace`.** Reconnaissance done, implementation deliberately not started this round (see the note on budget discipline below). What the measurement established:
  - **No new table and no migration are needed.** `run_events` is `(event_id TEXT PRIMARY KEY, run_id TEXT NOT NULL, payload TEXT NOT NULL, created_at INTEGER NOT NULL)` — the row already stores an arbitrary payload, so a trace can be one more row in the same table keyed `${runId}:trace:${toolCallId}`.
  - The pieces to touch, all three in one change: `RunEventInput` (TS + Rust) gains an **optional, explicit** `trace` field; `RunEventRecord`/`readRunEvents` may need to expose it; and `agentRunner` writes one row per trace.
  - **Why an explicit field instead of stuffing the trace into `detail`:** `RunEventVersions`' `deny_unknown_fields` exists so that smuggling `reasoning`/`imageBytes` into an event is a loud rejection. The same discipline argues for a declared `trace` struct with exactly the fields `ToolCallTrace` has — the boundary stays enumerable, which is the whole point.
  - **Ordering constraint:** `coordinator.toolTraces()` is only complete **after** the run, while events stream during it. So trace rows are written at the end of the run, not inline. That is a real durability difference from event rows (a crashed run keeps its events but loses its traces), and it should be stated rather than discovered.

It stops for exactly three reasons, each with a name: **no tool calls** (that round is the endpoint — it produced a plan, a clarification or an answer), **every requested call already executed** (idempotent stop, because re-executing would land the same action twice — the same discipline as "one alias, one id" in `draftStore`), and **budget exhausted** (`rounds` / `calls_per_round` / `tool_calls`, with the exhausted cell named so the coordinator can tell the truth about why it stopped).
  - It **executes only the fresh calls** when a retry mixes old and new ids, and `advanceToolLoop` counts only newly executed calls — otherwise a model that re-sends its batch would burn the tool budget without performing a single extra action.
  - It deliberately **does not invent its own quota**: limits are passed in by the caller and aligned with the one existing budget (`generation` 4 / `network` 6 / `tool` 24 in `budget.ts`). `budget.ts`'s header already records why a second counter is the failure mode to avoid ("6 network calls total" must not become "6 per category").
  - Why this slice first: the hard part of Phase 2 is not the loop, it is **not letting the loop run away**, and that is a set of criteria — which can be fully tested without running a coordinator. The remaining Phase 2 work is orchestration, not judgement.
- **Phase 3 sixth slice (2026-09-29): the gate is live in production runs** — `agentRunner` now declares acceptance criteria derived from the user's own words (`apps/web/src/agent/acceptance.ts`, 8 cases).
  - `deriveAcceptance(prompt)` returns `AcceptanceCheck[]`; `agentRunner` passes it to `coordinator.start` **only when non-empty**. Empty ⇒ nothing declared ⇒ the gate stays inert (behaviour byte-for-byte unchanged). This distinction matters: treating "the prompt contains nothing checkable" as "no evidence" would end every conversational request in failure.
  - The derivation is deliberately narrow, and **half its tests prove what it refuses to derive**, because a wrong criterion does not mean "one less check" — it means **a correct drawing gets blocked**:
    - **no `edge_length` from a bare number**: an edge-3 regular tetrahedron has a bounding box of `(3, 3·√2/2, 3·√2/2 ≈ 2.12)`, so comparing 3 would reject a *correct* document. Size checks need per-primitive-type conversion, which lives in the geometry kernel;
    - **no `has_label` from a noun**: "立方体" is an intent, not a required label text;
    - **no check at all** for requests that are not about creating geometry.
  - Three real over-claiming bugs were caught by those tests and fixed in the matcher, not the expectations:
    1. "把刚才的**截面**平面改一下" (modify a section) matched the section keyword — modifying and creating are different facts;
    2. "**画布**上有几个**点**？" matched via the "画" inside "画布" — a read-only question would have demanded a draggable point;
    3. "**棱柱**的截面怎么算？" matched while asking about a concept.
    Fixed with per-shape `exclude` lists (a global stop-word list would have removed "改" from *other* shapes' criteria too — a different bug).
  - Evidence that wiring it did not cause false rejections: the full `apps/web/src/agent/` suite and the whole 2966-case suite stay green with the gate live.
- **Phase 3 fifth slice (2026-09-29): the gate is now actually consulted by the coordinator** — the judgement chain is wired end to end.
  - `CommitterPort.stage`'s success result gained an optional `verification: VerificationReport`; `CommitRequest` and `StartRequest` gained an optional `acceptance`. The acceptance criteria travel **down** (only the caller knows them) and the report travels **back** (only the adapter can compute it, because only it holds `staged.preview.candidate`). The candidate document itself still never enters the coordinator, so it cannot leak into a model context.
  - The coordinator consults `verificationGate` after `validating` and before offering confirmation. Blocked runs land in **`failed`**, not `waiting`: `waiting` means "there is a question for the user", and there is none here — the transition table confirms it, since `validating`'s only legal successors are `awaiting_confirmation` / `compiling` / `failed`. It does not fall back to `compiling` either, because the gate carries no `RepairRequest` and a retry without one is a blind repeat.
  - **Behaviour is byte-for-byte unchanged for callers that declare no acceptance criteria** (`acceptance === undefined`): no verification runs, nothing is blocked, and no `acceptance` key is forwarded. That is pinned by a test, because "wired an optional feature" must not silently become "every run is now blocked".
  - Declaring an **empty** acceptance list is *not* the same as declaring none: `runAcceptance(document, [])` yields a `not_supported` report, and the gate blocks it. Pinned by a test.
  - 5 new coordinator cases cover the wiring itself (the criterion was already tested case by case in `completionGate.test.ts`); "the rule is written but nobody calls it" was exactly the state this slice removes.
  - **Honest gap:** `apps/web/src/agent/agentRunner.ts` does **not yet declare acceptance criteria**, so in production the gate is still inert — it is wired and enforced, but no caller feeds it. Turning it on for real runs is a separate step (building acceptance from the plan/user request).
  - **Process note (a self-inflicted error worth recording):** I used a blanket text replace to flip `phase()).toBe("waiting")` to `"failed"`, which damaged **two unrelated pre-existing tests**. I caught it from a test named "fails the run when preparation is refused" asserting `"failed"` *before* my change — a contradiction that only makes sense if my replace was the cause. Both were restored. A global replace across a 690-line test file is not an edit; it is a guess.
- **Phase 3 fourth slice (2026-09-29): the missing middle exists — acceptance criteria → verification report** (`verification/taskAcceptance.ts`, 9 cases).  - Before this slice the two ends existed but nothing joined them: `taskVerification` could check a document, `completionGate` could judge a report, but **nobody could say what a given run had to satisfy**. Task 3.1's `TaskSpec` had never been given a shape, so "verify this run" had nothing to verify against.
  - `AcceptanceCheck` is a **discriminated union** (`has_primitive` / `has_entity` / `edge_length` / `has_label` / `unsupported`), deliberately not the fixture shape `{type: string, expected?: ...}`. The fixture shape has to be writable by non-TypeScript readers, but at runtime a mistyped string `type` produces **no compile error and silently checks nothing**. The two shapes stay separate for that reason.
  - `runAcceptance(document, acceptance)` aggregates with the **same precedence as `taskVerification`** (`failed` > `not_supported` > `unknown` > `approximate` > `passed`) — two different aggregation rules in one codebase is how the same task gets judged two ways.
  - `acceptance: []` yields `not_supported`, **not** a pass: "this run declared no criteria" and "this run is verified" are different facts, and treating the first as the second is just "the model said it is done" in another costume.
  - `unsupported` conditions are carried through as `not_supported` rather than ignored, so "we did not verify this" can never read as "verified".
  - The end-to-end property is tested directly: conditions → report → `verificationGate`. Testing each segment separately and finding them all green while the chain blocks nothing is the classic failure of this kind of work, so the test goes through the gate.
  - **A repeat of a mistake worth recording**: `extentOf` first read coordinates only from top-level `x/y/z`, but `point3` stores them under `position` — so `edge_length` reported `unknown: cannot read the extent` for a perfectly good cube, and the gate would have blocked a correct drawing. This is the *same* coordinate-reading bug I fixed in `layoutModel.ts` one round earlier. The reading is now one exported `coordinatesOf` helper so a third copy cannot appear.
  - **Still not wired to the coordinator.** This slice completes the judgement chain (conditions → report → gate); what remains is *calling* it. That is a port change: `CommitterPort.stage` returns only `{draftVersion, previewHash}` and `DraftStorePort.stage` only `{draftId, draftVersion, previewHash}`, so the report has nowhere to travel back on. The adapter does hold the candidate document (`staged.preview.candidate`), which is where the run belongs.
- **Phase 3 third slice (2026-09-29): the completion criterion now exists as one testable definition** — `verification/completionGate.ts` (9 cases).
  - `verificationGate(report)` decides whether a run may proceed to confirmation / completion. It blocks: **no report at all**, `failed`, `not_supported` ("we did not verify" is not "verified"), `unknown`/`approximate` (inconclusive is not a pass), a `passed` report with **no checks**, and a `passed` report holding non-passing checks.
  - Precedence is deliberately aligned with `taskVerification`'s aggregation: `failed` > `not_supported` > `unknown`/`approximate` > self-inconsistency. A `passed` status containing a **failed** check is read as a **determinate failure** (the `status` field is wrong), not as a bookkeeping error — "self-inconsistent" sounds ignorable, and this is not.
  - Every rejection carries a `code` and `next_actions` **taken from the report's own failing checks**, so the coordinator cannot lose the specific location when deciding what to do next.
  - **This is deliberately a pure function, not yet called by the coordinator.** Keeping the criterion separate from the orchestration is what makes each rejection reason testable without running a whole run — but it also means the gate is **not yet enforced in production**, which is the honest remaining gap (see below).
  - Blocked on a port change: the coordinator never holds the candidate document. `CommitterPort.stage` returns only `{draftVersion, previewHash}` (and `DraftStorePort.stage` only `{draftId, draftVersion, previewHash}`), while `verifyTaskChecks` needs the document. Wiring the gate therefore needs either `stage` to return the candidate document or a dedicated verification port — a contract decision, not more judgement logic.
- **Phase 3 second slice (2026-09-29): the deterministic judge now covers sections and relations.**
  - New check types in `agentTaskJudge.ts`: `dependency_order`, `section_source`, `solid_unchanged`, `section_updated`. `agentTaskJudge.test.ts` adds 14 cases, each proving the judge **can also fail** — a judge that only ever passes carries no information and looks green while doing it.
  - The judgements are document queries, not tool-receipt checks: is the section's `sourceId` a real solid in the document; does every solid still resolve the vertices it claims (the real regression is "editing the section deleted the solid's vertices"); does each section carry a non-degenerate plane (zero normal ⇒ the plane was written as all zeros).

  - A defect `tsc` caught before it shipped: I had written `source.type === "prism"`, but there is no `prism` primitive type — a prism is a `polyhedron3` with `construction.kind === "prism"`. Left in, "a prism's section" would have failed forever while looking like "the model built no solid".
- **Phase 4 second slice (2026-09-29): the local layout path is now reachable from a run.**

## 2026-10-04 follow-up: geometry verification is live; next round is witness search, not a broader tool loop

The `b1ee3d3` slice adds a second semantic boundary on top of the typed tool loop: a static solid candidate may be confirmed only when supported obligations extracted from the user's text pass against the materialized candidate. Underdetermined geometry is valid when it is one verified instance; it is not a proof. Unknown obligations stay visible and block confirmation, including the HostBridge consent path.

This closes the specific “wrong diagram silently passed” class for the supported high-precision obligation forms. It does not supply real-provider accuracy, a general nonlinear solver, persistent drag constraints, screenshot judgment, or formal proof. The next design is therefore `docs/superpowers/specs/2026-10-04-agent-next-round-witness-search-design.md`: first unify obligation IR, then add bounded deterministic witness search, then measure real providers separately from `deterministic_local`.
